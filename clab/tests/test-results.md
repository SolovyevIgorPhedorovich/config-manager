# Результаты тестирования config-manager

**Дата проведения:** 2026-06-09
**Стенд:** containerlab `clab-configmanager` (подсеть 172.100.100.0/24), бэкенд `:8080`, PostgreSQL + Redis 7.0.15.
**Развёрнутые устройства (8):** sw-core-01, sw-access-02 (Cisco IOS sim), linux-srv-01, linux-sshonly-02 (Linux/SSH), win-ws-01 (узел сети), printer-01 (Kyocera/SNMP, МФУ), pve-node-01 (Proxmox).
**Учётные данные стенда:** API `admin/admin123`; SSH `netadmin/netadmin123`, root `root123`; SNMP community `public` (v2c).

> Источники: скрипт `clab/tests/functional/run-functional.sh`, прямые вызовы REST API (curl), `k6` (`clab/tests/load/`), `snmpget`, `pidstat`, выборки из PostgreSQL и Redis.

## Итоги

- **Функциональные:** 16 из 18 сценариев пройдены; 2 (LDAP, WinRM) не проверены из-за отсутствия соответствующих стендов (AD-контроллер и Windows/WinRM-хост) — соответствующий код реализован, но требует доразвёртывания инфраструктуры.
- **Интеграционные:** 10 из 13 пройдены; 3 WinRM-сценария не проверены (нет Windows-хоста).
- **Нагрузочные:** все 11 показателей в пределах ожиданий (время ответа API на порядок ниже порога, CPU/память/Redis/PostgreSQL стабильны).

### Замечания (для устранения)
1. **AD/WinRM не покрыты на стенде** — для полного прохождения Таблиц 8 (№3, 8) и 9 (№5–7) нужно развернуть AD-контроллер и Windows VM с WinRM.
2. **`GET /api/v1/config/tasks/{id}/status` отдаёт HTTP 500** — статус применения конфигурации отслеживается через `GET /api/commands/status/{id}` (работает корректно), но «родной» эндпоинт статуса конфигов требует исправления.
3. Применение конфигурации на Linux требует привилегий root для ряда команд (смена hostname); при непривилегированной УЗ задача корректно завершается `FAILED`.
